# 生成规则：从「To-be 流程 + 核心功能」到概念设计

> 本文件规定 6 段内容如何从输入**推导**出来（不是模板填空）。
> 目标：客户一眼看懂「做什么、AI 与人怎么分、一期做什么、分几阶段、试点在哪、要拍板什么」。

---

## 一、阶段序列（stages）

- 直接沿用 To-be 流程的**业务阶段序列**（P1…Pn），**不重画、不增删**。
- 每阶段的 `name`（短名）与 `full`（全称）取自 To-be；`ai[]` 与 `human` 取自各阶段的 AI/人分工。
- **禁止**把 To-be 泳道图（列=阶段 × 行=角色）整张搬进来——概念设计只要**阶段级**粒度。

## 二、AI / 人 / 人机协同（kind）

对每个能力项判定承担方：

| kind | 含义 | 判定 |
|---|---|---|
| `auto` | Agent 自动执行 | 取数 / 采集 / 校验 / 解读 / 生成 / 跟踪 / 沉淀等**高负荷、可结构化**的工作 |
| `hybrid` | 人机协同 | 需要人现场动作配合（拍照 / 语音 / 抄数 / 确认） |
| `manual` | 人工承担 | 判断与决策（确认目标、裁定主因、核定资源、拍板） |

- `human` 字段只写**判断与决策类**动作，不重复 AI 已承担的内容。
- 一条原则：**AI 承担高负荷，人承担判断与决策**——若某阶段两端都空，说明拆分没到位。

## 三、范围标注（scope / mvp）

- 有**一期切入范围**时：命中一期范围的能力标 `mvp: true`，其阶段 `scope` 取 `mvp` 或 `partial`（部分命中）；其余阶段标 `next`（紧随其后）/ `later`（后续）。
- 无一期范围时：按**常规推进**推导并在 `flowFoot` 标注「一期范围待客户确认」——
  惯例是「数据现状打底 → 采集与知识处理 → 解读校验 → 机会识别」为 MVP，「策略生成」紧随其后，「执行 / 复盘」后续。
- `scopeLabel` 用客户能懂的词：`★ 部分本轮` / `★ 本轮重点` / `下一步` / `后续`。

## 四、产品愿景（vision）

- `statement`：**定位一句话** = 服务谁 + 把什么（现状）变成什么（理想）。主语是目标用户，不是技术。
- `lead`：一句「不是什么、而是什么」，用于划边界（如「不是工具拼盘，而是全流程赋能」）。
- `principles`：2–4 条，从产品定位推导，**每条一句可执行的话**。常见三条：
  1. **服务一线**——第一对象是一线，不是管理者；
  2. **主动**——主动提问 / 提醒 / 引导，而非被动应答；
  3. **有回路**——收集 → 结论 → 验证 → 行动 → 结果回流。

## 五、第一期范围卡（phase1.focus）

每张卡 = 一个「本轮重点」，固定四要素：

| 字段 | 写什么 |
|---|---|
| 解决什么 | 现状痛点（缺什么、导致什么） |
| 怎么做 | 本轮用什么能力解决（采集方式 / 校验方式 / 生成方式） |
| 边界 | 人只做什么、合规底线、不做的事 |
| output（产出） | 交付物（可核对的形态，如「结构化情报：〔对象〕〔事实〕→〔含义〕」） |

- 卡数 2–4 张；**只放本轮重点**，不放全量能力。
- 每张卡的产出必须**可核对**（有形态、有字段），不能是「提升效率」这类空话。

## 六、试点范围（phase1.pilot）

- `business`：业务线 / 区域 / 规模（如「零售 + 渠道两条线，6 个典型省份」）。
- `rationale`：选点依据，2–4 条，常见维度：
  - 覆盖不同市场成熟度（成熟 + 成长兼顾）；
  - 数据基础与系统条件较好，便于交叉验证；
  - 团队配合度高，能先跑出可复用样本。

## 七、落地路线图（roadmap）

固定**三阶段**，每阶段七行：

| 行 | 一期 | 二期 | 三期 |
|---|---|---|---|
| 范围 | MVP（一期切入） | 补齐其余 AI 能力 + 深化 | 全流程稳定运行 + 延伸能力 |
| 能力 | 一期 AI 能力清单 | 新增能力清单 | 深化 + 新增（算账 / 谈判等） |
| 数据集成 | 打通一期所需数据源 | 扩展数据源、统一口径 | 全链路打通 |
| 知识库 | 一期知识入库 | 知识资产结构化、与情报库联动 | 知识飞轮（回流 + 迭代） |
| 覆盖 | 试点范围 | 推广到多数用户（给比例） | 多业务线共用 |
| 交付 | 一期交付物 | 二期交付物 | 三期交付物 |
| 衡量（`hl`） | 一期指标 | 二期指标 | 三期指标 |

> 指标要**可观测**（如有效情报数、采纳数、活跃用户覆盖），不写「提升效率」。

## 八、客户确认事项（confirm）

**归纳所有悬空决策点**，逐条给「事项 / 影响 / 需谁拍板」：

- **范围**：一期到底切哪几个阶段 / 能力？
- **边界**：合规底线（哪些不能采 / 不能记）、数据使用范围；
- **试点**：试点业务线 / 省份 / 名单；
- **指标**：一期用哪些指标衡量、目标值；
- **依赖**：需要客户提供的数据 / 系统权限 / 人员配合；
- **口径**：关键阈值 / 分类口径（标「领域专家假设值 · 待确认」）。

> 这一段是**客户确认稿的落点**：宁多列几条，也不要让悬空决策藏在正文里。

---

## 九、反例（禁止）

- ❌ 把概念设计写成工程规格（功能清单 / UI 组件 / 故事线 / 规则门禁）——那是 `agentic-product-proposal-generator` 的活。
- ❌ 阶段流水线照搬 To-be 泳道图，粒度过细。
- ❌ 一期范围不给客户可核对的产出物，只写「提升效率」。
- ❌ 路线图三阶段没有可观测指标。
- ❌ 第 6 段「客户确认事项」留空或只写「无」。
