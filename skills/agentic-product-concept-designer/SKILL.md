# Agentic Product Concept Designer (Agent 产品概念设计 · 客户确认稿)

在**初步确定 To-be 流程与核心功能之后**，先做一份**初步概念设计**交给客户确认——
回答「做什么、AI 与人各承担什么、第一期做哪些、分几阶段推进、试点在哪、需要客户拍板什么」。

> **性质**：本 Skill 产出的是**面向客户确认的概念层设计**，不是工程规格。
> 它把「To-be 流程 + 核心功能」翻译成客户能一眼看懂的**范围与分工**，用于对齐预期、锁定一期范围；
> 详细的施工级设计（功能 / UI / 故事线 / Agent 行为 / 规则门禁）由 `agentic-product-proposal-generator` 承担。

> **与相邻 Skill 的边界（避免误触发）**
> - 本 Skill **只做概念层**（愿景 / 阶段分工 / 一期范围 / 试点 / 路线图 / 待确认），**不写**功能清单、UI 组件、演示故事线、规则门禁。
> - `agentic-product-proposal-generator` = **工程级方案**（Markdown，给原型作者施工）；本 Skill = **客户确认稿**（可视化，给客户拍板）。两者是「先概念后施工」的关系。
> - 本 Skill **不重画 To-be 泳道图**（用 `to-be-process-designer`）；**不做**详细旅程（用 `ai-product-journey-generator`）、**不做**原型（用 `prototype-generator`）。
> - 本 Skill 的路线图是**产品能力演进**（一期 → 扩展 → 闭环）；通用商业路线图 / 里程碑用 `roadmap-generator` / `milestone-plan-generator`。

> [!IMPORTANT] 全局规范（双重输出 / 输出路径 / 视觉设计）
> **① 双重输出**：必须**同时**输出两个部分：
> 1. **结构化 YAML**：供自动化与复用（契约见 `references/schema.yaml`）。
> 2. **交互式 HTML**：面向客户确认的可视化报告（含「复制 YAML」）。
>
> **② 输出路径与命名**：
> - 目录：属具体 AI 场景 → **必须**放入 `<公司/业务名>/<场景名>/`。
> - 文件名：`[公司/业务名]-[场景名]-产品概念设计.yaml` / `.html`
>   （如 `X电商订舱-智能订舱Agent-产品概念设计.html`）。
> - **禁止**把真实产物写进本 Skill 的 `examples/`（examples/ 仅放脱敏演示样例）。
>
> **③ 视觉设计**：浅色底、内容区撑满；结构 = 顶部 hero（产品名 + 定位 + 关键 chips）
> → ① 产品愿景 → ② To-be 流程总览（阶段流水线）→ ③ AI 与人分工表 → ④ 第一期范围与试点
> → ⑤ 落地路线图 → ⑥ 客户确认事项。视觉规范见 `references/visual-spec.md`。

## 一、输入契约

| 输入 | 来源 | 用途 |
|---|---|---|
| **To-be 流程** | `to-be-process-designer`（阶段序列 + 各阶段 AI/人分工） | 生成阶段流水线与分工表 |
| **核心功能** | 场景定义 / 机会点 / 工作流（各阶段的 AI 能力清单） | 归位到阶段，标注 AI 承担项 |
| **一期切入范围**（可选） | 客户 / 项目共识 | 标注 MVP（紫色）与「下一步 / 后续」 |
| **试点范围**（可选） | 客户 / 项目共识 | 第一期范围的试点业务线 / 区域 / 选点依据 |
| **产品愿景**（可选） | 客户访谈 / 战略材料 | 定位一句话与设计原则 |

> 缺失项允许**降级**：无一期范围时按「P1 打底 → 采集解读 → 机会识别 → 策略生成 → 执行复盘」的常规推进推导，并在文中标注「一期范围待客户确认」。
> 完整字段契约见 `references/schema.yaml`。

## 二、输出架构（6 段）

| # | 段 | 内容 | 生成规则 |
|---|---|---|---|
| — | **hero** | 产品名 + 定位一句话 + 关键 chips（定位 / 形态 / 本次切入 / 试点） | 由愿景与试点提炼 |
| 1 | **产品愿景** | 定位一句话（引用块）+ 设计原则（2–4 条） | 原则从产品定位推导（如服务一线 / 主动 / 有回路） |
| 2 | **To-be 流程总览** | 阶段流水线：每阶段 = AI 承担能力 + 人承担 + 范围标注；图例（AI 自动 / 人机协同 / 人工承担 / 一期 MVP）；流程脚注 | 由 To-be 阶段序列 + 核心功能归位生成 |
| 3 | **AI 与人分工表** | 阶段 × AI 承担 × 人承担 × 本轮 | 与第 2 段同源，表格化便于逐行确认 |
| 4 | **第一期范围与试点** | 本轮重点卡（解决什么 / 怎么做 / 边界 / 产出）+ 试点范围与选点依据 | 由一期切入范围与试点共识生成 |
| 5 | **落地路线图** | 三阶段（范围 / 能力 / 数据集成 / 知识库 / 覆盖 / 交付 / 衡量） | 常规推导：MVP → 扩展推广 → 全流程闭环 |
| 6 | **客户确认事项** | 待确认清单（事项 / 影响 / 需谁拍板） | 归纳所有悬空决策点（范围 / 边界 / 试点 / 指标 / 依赖） |

> **第 6 段是本 Skill 区别于普通汇报的关键**：概念设计的目的是**客户确认**，
> 必须把「需要客户拍板的事项」显式列出，而不是只呈现设计结果。

详细生成规则见 `references/design-rules.md`。

## 三、工作流 SOP

### Step 1 · 收齐输入
- 读取 To-be 流程（阶段序列 + AI/人分工）与核心功能清单；
- 收集一期切入范围、试点范围、产品愿景（缺失则标注降级）。

### Step 2 · 归位阶段与分工
- 按 `references/design-rules.md`：把核心功能归位到各阶段，区分 AI 承担 / 人承担 / 人机协同；
- 依据一期范围给每个能力标 `mvp / next / later`。

### Step 3 · 生成概念设计 YAML
- 按 `references/schema.yaml` 装配 6 段字段，保存为
  `<公司/业务名>/<场景名>/<公司名>-<场景名>-产品概念设计.yaml`。

### Step 4 · 编译 HTML
```bash
python3 scripts/build_concept.py \
  "<公司/业务名>/<场景名>/<公司名>-<场景名>-产品概念设计.yaml" \
  "<公司/业务名>/<场景名>/<公司名>-<场景名>-产品概念设计.html"
```

### Step 5 · 交付
- 告知客户/用户浏览器打开 HTML：hero → 产品愿景 → 流程总览 → 分工表 → 第一期范围 → 路线图 → **客户确认事项**；
- 顶部可「复制 YAML」；同时汇报「待客户确认事项」清单。

## 七、输出呈现铁律（通用 · 强制）

> 产出是给**客户 / 业务方**看的最终报告，不是过程记录。以下五条**违反即返工**。

1. **语言**：一律用**严谨、克制的中文业务咨询语言**——有一说一；**有观点必给依据**（数据 / 规则 / 来源 / 口径）。
   禁止 AI 味大词与空话堆砌（「赋能、闭环、抓手、深度融合、全方位、数智化」等无实指表述）。
2. **禁止多余英文备注**：中文标题 / 小节后**不得**追加英文装饰。系统名 / 标准缩写（CRM、BI、KPI、ROI）可保留；不造装饰性英文。
3. **只输出结论与依据**：**禁止**把过程讨论写进正文——与用户的对话 / 反馈、修订说明、跨行业类比的过程推理等一律不进正文。
4. **口径与边界**：不确定的推断标 `[推断]` 并给依据；不臆造数据；假设与阈值标注「待客户确认」。
5. **交付前自检**：逐段问「客户能否据此拍板 / 这是否属于我们内部讨论」——不能拍板或属内部讨论的内容，删除或移出正文。

> **本 Skill 的显式例外**：第 6 段「客户确认事项」是**交付物的核心内容**（本稿目的就是请客户确认），
> 不适用上述第 3 条对「待确认信息」的禁止——该条禁止的是**内部过程讨论与制作说明**，不含面向客户的确认清单。
