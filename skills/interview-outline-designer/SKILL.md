# Interview Outline Designer (访谈提纲设计)

为一次「现状访谈」设计提纲：围绕还原**一线业务信息流「捕捉 → 处理 → 决策 → 复用」**的现状，
输出一份**可直接照着问、也能直接在题下记录**的简洁提纲。

> **性质**：本技能产出的是**访谈工具**（问题清单），不是访谈结果。
> 访谈结束后的记录整理，用 `interview-record-integrator`。

> 定位与上下游：
> - **上游输入**：访谈目的与对象（业务线 / 角色 / 典型客户 / 时长）。
> - **本 Skill**：按 3 大段骨架生成提纲（场景差异靠术语替换 + 探针内嵌）。
> - **下游衔接**：`interview-record-integrator`（访谈后把录音 + 人工记录整理为待确认稿）→
>   `business-process-deep-analyzer` / `problem-definition`（现状与问题定义）。

> **与相邻 Skill 的边界（避免误触发）**
> - 本 Skill **只设计提纲**，不整理访谈记录（用 `interview-record-integrator`）。
> - 本 Skill **不做访谈后分析**（泳道图 / 问题定义 / 机会地图分别用对应技能）。
> - 本 Skill **不产出填写模板 / 受访者版 / 附录**——提纲本身就是现场记录纸。

> [!IMPORTANT] 全局规范（输出形态 / 输出路径 / 铁律）
> **① 输出形态（显式例外）**：本 Skill **只输出单一 Markdown 提纲**，不出 YAML、不出 HTML。
> 按 `skill-creator` 规范，属需显式声明的输出例外。
>
> **② 输出路径与命名**：
> - 目录：与调研材料同目录（通常 `<客户>/<场景>/` 下，按其既有约定存放）。
> - 文件名：`[业务线/场景]-现状访谈提纲.md`（如 `零售-现状访谈提纲.md`）。
> - **禁止**把真实提纲写进本技能的 `examples/`（examples/ 仅放脱敏演示样例）。
>
> **③ 铁律（违反即返工）**：只出提纲本体；3 大段结构；**不新增段落、不加附录、不写填写模板**；
> 简洁优先（见 `references/conciseness.md`）。

---

## 一、核心原则

1. **提纲即记录纸**：现场直接在题目下方记录（沿用打标 🟢 事实 / 🟡 感受 / 🔵 期望）。
   因此**不另出「现场记录模板」**——那正是实际使用中最冗余、从不被使用的部分。
2. **固定 3 大段骨架**：场景差异只做**术语替换 + 探针内嵌到对应问题**，**不新增段落**。
3. **简洁**：每小节 ≤ 4 题；★ 必问 ≤ 40%；单册目标 ≤ 约 45 题 / 100 行。
4. **只还原现状**：不评价、不引导到方案；避免「如果有个工具你会不会……」这类假设式提问。

---

## 二、3 大段骨架（压缩后）

| 段 | 内容 | 覆盖的信息流 |
|---|---|---|
| **一、角色与业务背景** | 角色与团队 / 目标与考核口径 / 核心业务全周期 / 拓展与来源（可选） | 提供语境 |
| **二、信息流现状** | 信息捕捉与研究 / 信息分析与判断 / 信息处理、决策与记录 | 捕捉 → 处理 → 决策 → 复用 |
| **三、理想态与资源重排** | 理想方式 / 资源重排（投射题）/ 管理者视角 | 理想态 |

> 骨架是**通用模板**：「核心业务全周期」按场景实例化——销售线为「客户全生命周期」、
> 服务线为「工单全流程」、项目线为「项目全周期」、职能线为「事项处理全流程」；
> 「拓展与来源」仅在角色有获客 / 接单 / 新增环节时保留，否则删去。
> **更短的场次（约 60 min）可压成 2 大段**：把「三、理想态」并入「二、信息流现状」的末尾
> （信息流现状与理想态）。默认用 3 大段；时长紧张时用 2 大段。
>
> 完整问题模板见 `references/skeleton.md`。

---

## 三、场景适配（不新增段落）

不同业务线 / 场景（销售、服务、运营、生产、职能……）差异通过两步实现：

1. **术语替换**：把骨架里的占位词换成该场景的说法
   （如「客户 / 终端 / 交易凭证 / 成效口径 / 层级」）。
2. **探针内嵌**：把该场景特有的 2–4 个探针**并入最相关的既有问题**（作为 ⤷ 追问），
   **不另起小节、不加附录**。

> 占位词表、场景示例、探针与「新场景推导法」见 `references/line-variants.md`。

## 四、工作流 SOP

### Step 1 · 明确输入
- 访谈目的（默认：还原一线业务信息流「捕捉 → 处理 → 决策 → 复用」现状）、
  业务线 / 场景、受访角色、典型对象、时长。

### Step 2 · 取骨架
- 以 `references/skeleton.md` 的 3 大段为骨架；时长紧张 → 用 2 大段。

### Step 3 · 场景适配
- 按 `references/line-variants.md` 替换术语、内嵌探针。

### Step 4 · 按简洁铁律瘦身
- 按 `references/conciseness.md`：删重复、控题量、控 ★ 比例、压缩使用说明为 4 行。

### Step 5 · 输出与自检
- 输出单一 Markdown 到与调研材料同目录；
- 过一遍文末 QA 清单。

## 八、输出呈现铁律（通用 · 强制）

> 产出是给**访谈团队**用的工作文件，不是过程记录。以下六条**违反即返工**。

1. **语言**：一律用**严谨、克制的中文业务语言**——有一说一；不堆砌空话。
2. **禁止多余英文备注**：中文标题 / 小节后**不得**追加英文装饰。系统名 / 标准缩写（CRM、BI、KPI、ROI）可保留；不造装饰性英文。
3. **只保留提纲本身**：不写制作说明、修订记录、与访谈无关的讨论。
4. **口径与边界**：不确定的业务术语标 `[待确认]`；不臆造业务概念。
5. **交付前自检**：逐题问「这道题能拿到一个可核对的事实吗」——拿不到的题删掉或改问。
6. **精炼优先**：**只保留必要段落**——删除一切辅助描述、方法论 / 流程 / 制作层说明、示例性长文与重复表述；模板用**最小占位符**，不得用示例内容充数。
