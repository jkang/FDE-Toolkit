参考对象
调拨单（Transfer Order）

系统生成的到货计划文件，说明预期到货的 SKU 和数量，不等于实际收货

status enum
pending / in_transit / delivered / cancelled
expected_skus string
预计到货的 SKU 列表
eta datetime
预计到店时间
source_location string
货物来源仓库或门店
⚠️ 概念边界
≠ 调拨单只证明「预计」到货，不能用作实际库存依据
≠ 调拨单 delivered ≠ 门店已完成收货扫描
≠ 调拨单数量 ≠ 实际到货数量（可能有差异）
事件对象
到货记录（Delivery）

货物实际到达门店的事件记录，含到店时间和箱数，是收货核验的起点

carton_count number
实际到达箱数
arrival_time datetime
实际到店时间
signed_by string
签收人
⚠️ 概念边界
≠ 到货记录只证明货到了门店，不证明已完成 SKU 核验
≠ 箱数到齐不代表 SKU 和数量正确
事件对象
箱号扫描（Carton Scan）

对每个到货箱子进行扫描，确认 SKU、尺码、颜色和数量的实际记录

sku_id string
扫描的 SKU 编码
color string
颜色
size string
尺码
quantity_received number
实际到货数量
has_discrepancy boolean
是否存在差异
⚠️ 概念边界
≠ 只有完成 Carton Scan 的 SKU 才能被视为可用库存
≠ 存在差异未关闭时，受影响 SKU 不能进入上架流程
核心对象
陈列位置（Fixture）

门店内的物理陈列空间，活动陈列和日常补货均依赖其可用状态

status enum
available / occupied / reserved
assigned_campaign string
已分配的活动名称（occupied 时）
location string
门店内位置描述
⚠️ 概念边界
≠ Fixture occupied 时不能开始新活动陈列准备，即使活动日期紧迫
≠ Fixture reserved 仅表示规划，不代表已释放可用
参考对象
活动（Campaign）

商品推广活动，通常要求特定陈列位置、特定商品到位和上市前准备工作

launch_date datetime
上市日期
required_skus string
活动必须到位的 SKU 列表
required_fixtures string
活动所需陈列位置
prep_tasks string
上市前须完成的准备任务列表
⚠️ 概念边界
≠ 活动上市日期临近不代表准备工作已完成
≠ 活动计划存在 ≠ 活动物料和商品已到位
参考对象
员工（Staff）

门店员工，具备不同技能，某些任务（如 VM 陈列）只能由认证员工执行

skills string
技能标签，如 VM（视觉陈列）
shift_status enum
on_shift / confirmed / unconfirmed
⚠️ 概念边界
≠ 员工在班 ≠ 具备对应任务技能
≠ 员工「可能」到店 ≠ 已确认可用产能，不能计入计划
核心对象
撤货清单（Pullback List）

指示门店哪些商品需要从陈列撤回、打包发出的操作清单

sku_list string
需要撤货的 SKU 列表
deadline datetime
撤货完成截止时间
⚠️ 概念边界
≠ 撤货清单上的商品可能仍在陈列位置占用中，需先完成撤货才能释放 Fixture

情境 1
活动上市日期临近（48小时内）
活动上市日期在 48 小时内，需要确认商品到货、陈列位置和准备工作的实际状态
📋 Required Evidence
Delivery record / Carton scan
活动相关 SKU 是否已实际到店并完成扫描，无未关闭差异
Fixture status
活动所需陈列位置是否为 available 状态
Store task list
熨烫、打标、暂存、上架等准备工作是否已全部完成
✅ Valid Actions
检查活动相关 SKU 的到货和扫描状态
检查活动所需陈列位置当前状态
盘点剩余准备工作清单并评估是否能在上市前完成
如存在阻塞条件，标记活动准备风险并触发升级
❌ Invalid Actions
在未核验 Carton scan 前，标记活动商品已到位
原因：调拨单不能证明实际收货，标记会产生错误假设并延误风险识别
在 Fixture 仍被占用时，开始新活动陈列准备
原因：会与现有陈列产生物理冲突，且旧陈列未完成撤货
仅凭调拨单或上级口头确认，宣布活动已就绪
原因：调拨单 ≠ 实际收货，口头确认无可验证证据
⚠️ Exception Triggers
当：活动上市日期临近，但关键 SKU 的 Delivery 显示延迟或未到店
→ 标记活动准备风险，升级至商品计划团队评估影响范围
当：活动所需 Fixture 在上市 24 小时前仍处于 occupied 状态
→ 标记陈列位置冲突，触发跨团队协调流程
当：准备任务工时预估显示无法在上市前完成
→ 触发门店经理升级，评估推迟或应急方案
情境 2
货物已到店但扫描未完成
Delivery 记录显示货已到店，但 Carton scan 尚未完成，或扫描发现差异待处理
📋 Required Evidence
Delivery record
确认实际到货箱数
Carton scan records
已扫描箱数、发现差异的 SKU 列表
✅ Valid Actions
按箱号逐一扫描并记录实际 SKU、尺码、颜色和数量
发现差异时立即记录并开启异常工单
跟进差异关闭进度
扫描完成后确认可用 SKU 清单，通知下游流程
❌ Invalid Actions
将未扫描的商品直接计入可用库存或上架
原因：未扫描 SKU 的实际数量未经证实，可能导致库存错误
差异未关闭时将受影响 SKU 推入上架或活动准备
原因：差异可能导致实际数量与系统不符，会影响后续履约
⚠️ Exception Triggers
当：到货箱数少于调拨单预期，且缺口影响活动或顾客承诺
→ 立即标记差异并通知商品计划团队评估补货或承诺调整
情境 3
多类型任务并行且技能资源紧张
当天需要完成活动陈列（需 VM 技能）、到货支持和撤货，但具备 VM 技能的员工数量有限
📋 Required Evidence

Task list
各任务对技能的要求及预计所需工时
✅ Valid Actions
优先将已确认在班的 VM 技能员工分配至活动陈列任务
将不需要特殊技能的任务（到货搬运、撤货打包）分配给普通员工
调整后回到计划看板确认整体执行状态无遗漏
❌ Invalid Actions
将 unconfirmed 员工计入活动陈列的可用产能
原因：未确认员工无法保证到场，会导致活动陈列无人执行
将 VM 技能员工用于不需要该技能的搬运或撤货任务
原因：稀缺技能资源被低效占用，活动陈列任务可能无人处理
⚠️ Exception Triggers
当：唯一的 VM 技能员工临时无法到班
→ 立即升级门店经理，评估推迟活动陈列或从其他门店借调

# 业务本体：门店备货执行-Agent本体设计
领域：零售门店执行
Agent 角色：门店执行协调助手（Store Execution Assistant）
场景：门店从接收调拨计划到完成收货核验、活动陈列准备和人员安排的端到端执行场景

## 1. 核心业务对象与概念边界
### 调拨单（Transfer Order） [参考对象]
- 定义：系统生成的到货计划文件，说明预期到货的 SKU 和数量，不等于实际收货
- 属性定义：
  * status (enum)（可选值：pending / in_transit / delivered / cancelled） - 调拨状态
  * expected_skus (string) - 预计到货的 SKU 列表
  * eta (datetime) - 预计到店时间
  * source_location (string) - 货物来源仓库或门店
- 关键概念边界（不可混淆）：
  ⚠️ 调拨单只证明「预计」到货，不能用作实际库存依据
  ⚠️ 调拨单 delivered ≠ 门店已完成收货扫描
  ⚠️ 调拨单数量 ≠ 实际到货数量（可能有差异）
### 到货记录（Delivery） [事件对象]
- 定义：货物实际到达门店的事件记录，含到店时间和箱数，是收货核验的起点
- 属性定义：
  * carton_count (number) - 实际到达箱数
  * arrival_time (datetime) - 实际到店时间
  * signed_by (string) - 签收人
- 关键概念边界（不可混淆）：
  ⚠️ 到货记录只证明货到了门店，不证明已完成 SKU 核验
  ⚠️ 箱数到齐不代表 SKU 和数量正确
### 箱号扫描（Carton Scan） [事件对象]
- 定义：对每个到货箱子进行扫描，确认 SKU、尺码、颜色和数量的实际记录
- 属性定义：
  * sku_id (string) - 扫描的 SKU 编码
  * color (string) - 颜色
  * size (string) - 尺码
  * quantity_received (number) - 实际到货数量
  * has_discrepancy (boolean) - 是否存在差异
- 关键概念边界（不可混淆）：
  ⚠️ 只有完成 Carton Scan 的 SKU 才能被视为可用库存
  ⚠️ 存在差异未关闭时，受影响 SKU 不能进入上架流程
### 陈列位置（Fixture） [核心对象]
- 定义：门店内的物理陈列空间，活动陈列和日常补货均依赖其可用状态
- 属性定义：
  * status (enum)（可选值：available / occupied / reserved） - 当前可用状态
  * assigned_campaign (string) - 已分配的活动名称（occupied 时）
  * location (string) - 门店内位置描述
- 关键概念边界（不可混淆）：
  ⚠️ Fixture occupied 时不能开始新活动陈列准备，即使活动日期紧迫
  ⚠️ Fixture reserved 仅表示规划，不代表已释放可用
### 活动（Campaign） [参考对象]
- 定义：商品推广活动，通常要求特定陈列位置、特定商品到位和上市前准备工作
- 属性定义：
  * launch_date (datetime) - 上市日期
  * required_skus (string) - 活动必须到位的 SKU 列表
  * required_fixtures (string) - 活动所需陈列位置
  * prep_tasks (string) - 上市前须完成的准备任务列表
- 关键概念边界（不可混淆）：
  ⚠️ 活动上市日期临近不代表准备工作已完成
  ⚠️ 活动计划存在 ≠ 活动物料和商品已到位
### 员工（Staff） [参考对象]
- 定义：门店员工，具备不同技能，某些任务（如 VM 陈列）只能由认证员工执行
- 属性定义：
  * skills (string) - 技能标签，如 VM（视觉陈列）
  * shift_status (enum)（可选值：on_shift / confirmed / unconfirmed） - 当日班次状态
- 关键概念边界（不可混淆）：
  ⚠️ 员工在班 ≠ 具备对应任务技能
  ⚠️ 员工「可能」到店 ≠ 已确认可用产能，不能计入计划
### 撤货清单（Pullback List） [核心对象]
- 定义：指示门店哪些商品需要从陈列撤回、打包发出的操作清单
- 属性定义：
  * sku_list (string) - 需要撤货的 SKU 列表
  * deadline (datetime) - 撤货完成截止时间
- 关键概念边界（不可混淆）：
  ⚠️ 撤货清单上的商品可能仍在陈列位置占用中，需先完成撤货才能释放 Fixture

## 2. 对象关系依赖（Relationships）
- 【调拨单（Transfer Order）】 --(触发, 基数 1:N)--> 【到货记录（Delivery）】
  说明：一张调拨单可能对应多次到货记录（分批到货）
- 【到货记录（Delivery）】 --(包含, 基数 1:N)--> 【箱号扫描（Carton Scan）】
  说明：一次到货包含多个箱子，每个箱子需要独立扫描
- 【活动（Campaign）】 --(依赖, 基数 N:N)--> 【陈列位置（Fixture）】
  说明：活动需要特定陈列位置处于 available 状态
- 【活动（Campaign）】 --(依赖, 基数 N:N)--> 【箱号扫描（Carton Scan）】
  说明：活动需要相关 SKU 已完成收货扫描才能开始陈列准备
- 【员工（Staff）】 --(执行, 基数 N:N)--> 【活动（Campaign）】
  说明：具备 VM 技能的员工才能执行活动陈列准备工作
- 【撤货清单（Pullback List）】 --(约束, 基数 N:N)--> 【陈列位置（Fixture）】
  说明：撤货完成前，相关 Fixture 处于 occupied 状态无法释放

## 3. 行动边界限制（情境 - 证据 - 合法/禁止动作）
### 情境：活动上市日期临近（48小时内）
描述：活动上市日期在 48 小时内，需要确认商品到货、陈列位置和准备工作的实际状态
必须核实的证据：
  - [Delivery record / Carton scan] 活动相关 SKU 是否已实际到店并完成扫描，无未关闭差异
  - [Fixture status] 活动所需陈列位置是否为 available 状态
  - [Store task list] 熨烫、打标、暂存、上架等准备工作是否已全部完成
✅ 合法动作（允许执行）：
  - 检查活动相关 SKU 的到货和扫描状态
  - 检查活动所需陈列位置当前状态
  - 盘点剩余准备工作清单并评估是否能在上市前完成
  - 如存在阻塞条件，标记活动准备风险并触发升级
❌ 禁止动作（严禁执行，防范错误假设）：
  - 在未核验 Carton scan 前，标记活动商品已到位 （禁止原因：调拨单不能证明实际收货，标记会产生错误假设并延误风险识别）
  - 在 Fixture 仍被占用时，开始新活动陈列准备 （禁止原因：会与现有陈列产生物理冲突，且旧陈列未完成撤货）
  - 仅凭调拨单或上级口头确认，宣布活动已就绪 （禁止原因：调拨单 ≠ 实际收货，口头确认无可验证证据）
⚠️ 异常触发规则：
  - 当满足条件【活动上市日期临近，但关键 SKU 的 Delivery 显示延迟或未到店】 → 必须执行：标记活动准备风险，升级至商品计划团队评估影响范围
  - 当满足条件【活动所需 Fixture 在上市 24 小时前仍处于 occupied 状态】 → 必须执行：标记陈列位置冲突，触发跨团队协调流程
  - 当满足条件【准备任务工时预估显示无法在上市前完成】 → 必须执行：触发门店经理升级，评估推迟或应急方案
### 情境：货物已到店但扫描未完成
描述：Delivery 记录显示货已到店，但 Carton scan 尚未完成，或扫描发现差异待处理
必须核实的证据：
  - [Delivery record] 确认实际到货箱数
  - [Carton scan records] 已扫描箱数、发现差异的 SKU 列表
✅ 合法动作（允许执行）：
  - 按箱号逐一扫描并记录实际 SKU、尺码、颜色和数量
  - 发现差异时立即记录并开启异常工单
  - 跟进差异关闭进度
  - 扫描完成后确认可用 SKU 清单，通知下游流程
❌ 禁止动作（严禁执行，防范错误假设）：
  - 将未扫描的商品直接计入可用库存或上架 （禁止原因：未扫描 SKU 的实际数量未经证实，可能导致库存错误）
  - 差异未关闭时将受影响 SKU 推入上架或活动准备 （禁止原因：差异可能导致实际数量与系统不符，会影响后续履约）
⚠️ 异常触发规则：
  - 当满足条件【到货箱数少于调拨单预期，且缺口影响活动或顾客承诺】 → 必须执行：立即标记差异并通知商品计划团队评估补货或承诺调整
### 情境：多类型任务并行且技能资源紧张
描述：当天需要完成活动陈列（需 VM 技能）、到货支持和撤货，但具备 VM 技能的员工数量有限
必须核实的证据：
  - [Staff shift list] 具备 VM 技能的员工是否在班且已确认到店（非 unconfirmed）
  - [Task list] 各任务对技能的要求及预计所需工时
✅ 合法动作（允许执行）：
  - 优先将已确认在班的 VM 技能员工分配至活动陈列任务
  - 将不需要特殊技能的任务（到货搬运、撤货打包）分配给普通员工
  - 调整后回到计划看板确认整体执行状态无遗漏
❌ 禁止动作（严禁执行，防范错误假设）：
  - 将 unconfirmed 员工计入活动陈列的可用产能 （禁止原因：未确认员工无法保证到场，会导致活动陈列无人执行）
  - 将 VM 技能员工用于不需要该技能的搬运或撤货任务 （禁止原因：稀缺技能资源被低效占用，活动陈列任务可能无人处理）
⚠️ 异常触发规则：
  - 当满足条件【唯一的 VM 技能员工临时无法到班】 → 必须执行：立即升级门店经理，评估推迟活动陈列或从其他门店借调
### 情境：顾客取货承诺兑现确认
描述：顾客有预约取货记录，需要确认对应 SKU 实际库存可用后才能通知顾客取货
必须核实的证据：
  - [Carton scan / Stock records] 顾客预约 SKU 是否有实际确认的可用库存
✅ 合法动作（允许执行）：
  - 核实顾客预约 SKU 的实际库存状态
  - 库存确认可用后，通知顾客取货时间
  - 库存不足时，主动联系顾客说明情况并提供替代方案
❌ 禁止动作（严禁执行，防范错误假设）：
  - 仅凭调拨单预计数量，提前向顾客承诺取货时间 （禁止原因：调拨单 ≠ 实际到货，过早承诺会导致顾客体验受损）
⚠️ 异常触发规则：
  - 当满足条件【顾客取货日期临近，但所需 SKU 仍在延迟到货状态】 → 必须执行：主动联系顾客说明延迟，重新约定取货时间或讨论退款

## 4. 状态流转与全局护栏（Workstreams & States）
### 执行流（Workstream）：到货接收
描述：从接收调拨计划到完成 SKU 核验、处理差异的完整执行流
锚点对象：调拨单（Transfer Order）、到货记录（Delivery）、箱号扫描（Carton Scan）
状态节点及迁移路径：
  - 状态：预计到货 (s_pending_arrival)
    状态定义：调拨单已下发，货物尚在运输中，门店可见证据仅为调拨单数据
    可用的状态转移路径：
      * --[确认到货状态] (核实证据: Delivery record 显示货已到店，箱数已签收)--> 到达状态 到货待扫描 (性质: 正常迁移)
      * --[检查 ETA 或 Delivery status] (核实证据: Delivery status 显示延迟，或 ETA 已过仍无 Delivery 记录)--> 到达状态 到货延迟 (性质: 异常分支)
  - 状态：到货待扫描 (s_arrived_unscanned)
    状态定义：货已到店（Delivery record 存在），但 Carton scan 尚未完成，商品不可用
    可用的状态转移路径：
      * --[完成所有箱号扫描并核验] (核实证据: 全部 Carton scan 完成，无差异记录)--> 到达状态 收货完成 (性质: 正常迁移)
      * --[记录差异并开启异常工单] (核实证据: Carton scan 发现 SKU/数量/尺码不符)--> 到达状态 差异处理中 (性质: 异常分支)
  - 状态：差异处理中 (s_discrepancy)
    状态定义：扫描发现差异，异常工单已开启，受影响 SKU 暂不可进入后续流程
    可用的状态转移路径：
      * --[跟进并关闭差异工单] (核实证据: exception ticket 显示差异已关闭或经授权处理)--> 到达状态 收货完成 (性质: 异常恢复)
  - 状态：收货完成 (s_receiving_complete)
    状态定义：所有 SKU 已扫描核验，差异已处理，商品可进入上架和活动准备流程
  - 状态：到货延迟 (s_delayed)
    状态定义：到货已超出预期时间或 Delivery 状态显示延迟，门店需等待并追踪
    可用的状态转移路径：
      * --[确认新 ETA 并等待实际到货] (核实证据: Delivery record 显示货已到店)--> 到达状态 到货待扫描 (性质: 异常恢复)
🔒 全局不可绕过护栏规则：
  - 调拨单只能证明预计到货，不能用作实际库存或上架依据
  - 未完成 Carton scan 的 SKU 不能进入上架或活动准备流程
  - 差异未关闭时，受影响 SKU 不能被视为已确认可用
  - 到货延迟不能通过直接修改系统状态跳过，必须等待实际到货证据
🔗 跨流依赖关系：
  - 自身在该工作流时，若另一执行流 【活动陈列准备】 满足条件【活动相关 SKU 处于 s_discrepancy 或 s_delayed 状态】，则受到影响：活动准备流程被阻塞，需立即标记活动准备风险
  - 自身在该工作流时，若另一执行流 【常规补货】 满足条件【常规补货 SKU 到达 s_receiving_complete 状态】，则受到影响：常规补货流程解除等待，可继续推进上架
### 执行流（Workstream）：活动陈列准备
描述：从确认活动商品到货到完成陈列准备、活动可上线的执行流
锚点对象：活动（Campaign）、陈列位置（Fixture）、箱号扫描（Carton Scan）、员工（Staff）
状态节点及迁移路径：
  - 状态：等待商品到位 (cp_waiting_goods)
    状态定义：活动已计划，但关联 SKU 尚未完成收货扫描，不能开始陈列准备
    可用的状态转移路径：
      * --[确认活动相关 SKU 的 Carton scan 完成] (核实证据: 所有活动 SKU 的 Carton scan 完成，无未关闭差异)--> 到达状态 商品已到位 (性质: 正常迁移)
      * --[检查关联到货延迟风险] (核实证据: 活动 SKU 对应 Delivery 显示延迟且上市日期临近)--> 到达状态 准备有风险 (性质: 异常分支)
  - 状态：商品已到位 (cp_goods_ready)
    状态定义：活动 SKU 已完成收货扫描，等待陈列位置释放
    可用的状态转移路径：
      * --[确认 Fixture 可用后开始陈列准备] (核实证据: Fixture status = available，所有活动 SKU 已收货)--> 到达状态 准备进行中 (性质: 正常迁移)
      * --[检查 Fixture 冲突状态] (核实证据: Fixture status = occupied 且活动上市日期在 24 小时内)--> 到达状态 准备有风险 (性质: 异常分支)
  - 状态：准备进行中 (cp_in_progress)
    状态定义：陈列准备工作正在执行（熨烫、打标、上架、陈列调整），需要 VM 技能员工
    可用的状态转移路径：
      * --[确认所有准备任务完成] (核实证据: Store task list 中活动准备任务全部标记完成)--> 到达状态 活动已就绪 (性质: 正常迁移)
  - 状态：活动已就绪 (cp_ready)
    状态定义：所有准备工作完成，陈列已设置，活动可以按计划上线
  - 状态：准备有风险 (cp_at_risk)
    状态定义：活动准备存在阻塞（商品延迟 / Fixture 占用 / 准备工作不足），需升级处理
    可用的状态转移路径：
      * --[等待商品延迟解决] (核实证据: Delivery 延迟已解除，新 ETA 已确认)--> 到达状态 等待商品到位 (性质: 异常恢复)
      * --[Fixture 释放后继续准备] (核实证据: Fixture status 已变为 available)--> 到达状态 准备进行中 (性质: 异常恢复)
🔒 全局不可绕过护栏规则：
  - Fixture occupied 时不能开始新活动陈列，即使活动日期紧迫
  - 活动 SKU 未完成 Carton scan 不能开始陈列准备
  - 不能仅凭上级口头确认将活动标记为已就绪

### 执行流（Workstream）：常规补货
描述：基于门店库存水平，将到货商品补货到销售楼面的执行流
锚点对象：箱号扫描（Carton Scan）、陈列位置（Fixture）
状态节点及迁移路径：
  - 状态：等待收货完成 (rp_waiting_receiving)
    状态定义：补货所需 SKU 尚未完成收货扫描，无法确认可用库存
    可用的状态转移路径：
      * --[确认相关 SKU 收货完成] (核实证据: 相关 SKU 的 Carton scan 完成，无未关闭差异)--> 到达状态 可执行补货 (性质: 正常迁移)
  - 状态：可执行补货 (rp_ready_to_replenish)
    状态定义：SKU 已收货确认，Fixture 可用，可以执行上架补货
    可用的状态转移路径：
      * --[完成上架并更新库存] (核实证据: 商品已上架，库存系统已更新)--> 到达状态 补货完成 (性质: 正常迁移)
  - 状态：补货完成 (rp_complete)
    状态定义：商品已完成上架，楼面库存已更新
🔒 全局不可绕过护栏规则：
  - 未完成 Carton scan 的 SKU 不能进入补货上架流程
  - 活动专属 SKU 在活动陈列准备完成前，不能用于常规补货上架
🔗 跨流依赖关系：
  - 自身在该工作流时，若另一执行流 【到货接收】 满足条件【补货 SKU 完成收货】，则受到影响：常规补货流程解除等待，进入可执行状态
