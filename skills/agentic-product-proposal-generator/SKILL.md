# Agent Product Proposal Generator

本技能承接 FDE 方法**理需求 / 场景定义 / 挖知识 / 梳理本体**的既有产出，以及 `persona-journey-designer` 的《**用户画像与典型旅程**》，统一聚合为一份「**产品方案**」——一份可直接交给原型作者照单施工的**工程级设计文档**（Markdown）。

它不是模板填空，而是一个**翻译/聚合引擎**：把「知识挖掘出的规则、决策因子、阈值、硬/软约束」与「本体梳理出的实体/关系/动作/状态」，翻译成「产品形态、故事线 mock 数据、UI 交互、HITL 拦截、规则消费门禁」。

> [!IMPORTANT]
> **输出格式例外声明（本 Skill 不走视觉双重输出）**:
> 本 Skill 产物是**一份 Markdown 设计文档**（如「分仓智能补货 · 产品方案 v2」），是给原型作者/开发照单施工的**规格文档**，**不是**可视化报告。因此**不**输出交互式 HTML，也不做 design.md 视觉渲染；仅输出单一 Markdown。此为双重输出规范的**显式例外**，仅适用于本 Skill。
>
> **输出路径与命名规范 (Output Path & Naming Convention)**:
> - **目录**: 产物属于具体 AI 场景 → **必须**放入 `<公司/业务名>/<场景名>/` 场景子目录（两层规范）。
> - **文件名**: 场景级 Markdown 命名 `[公司/业务名]-[场景名]-产品方案.md`（例如：`X电商订舱-智能订舱Agent-产品方案.md`）。
>
> **配套资产规范**:
> - 同一场景若需要结构化数据（供下游/复用），可另输出 `[公司/业务名]-[场景名]-产品方案.schema.yaml`（可选，依据 `references/schema.yaml`）。
>
> **可选预览 HTML（非双重输出必需）**：
> 若需在浏览器/统一报告仪表盘中浏览 Markdown，可运行 `scripts/build_proposal_preview.py <产品方案.md> <输出.html>`（用法见脚本 docstring）生成**单文件自包含预览**（marked + mermaid CDN 客户端渲染，样式对齐 Refresher Workshop 主题），供 iframe 内嵌与人工审阅。该 `.html` 仅为 Markdown 的**可视化预览**，不是双重输出所要求的结构化产物，亦不改变本 Skill「单一 Markdown」的例外口径。

## 一、输入契约（上游产物）

本 Skill 依赖上游四项产出的**字段映射**，完整契约见 `references/input_contract.md`。缺失项允许**降级**（用现有产出代理 + 文档显式标注），但必须写明「用哪份代理」。

| 阶段 | 上游产物 | 关键字段 | 供本 Skill 使用 |
|---|---|---|---|
| 理需求 | 业务主体与画像 / 业务现状全景 / 需求场景全景 | 业务领域、价值流、痛点、证据 | 产品定位、非目标、业务价值高光 |
| 场景定义 | AI 场景画布 + 数据/知识资产盘点 | 痛点、用户角色、输入输出、businessGains、CKD | 定位一句话、使用者、KPI/价值、功能边界 |
| 用户画像 | 用户画像与典型旅程（`persona-journey-designer`） | 画像、典型场景、Job Story、起点→终点、产品介入点 | 第 3 段故事线划分（按画像 × 场景）、每条故事线的用户目标与端到端旅程 |
| 挖知识 | 任务流程挖掘清单(L5) + 任务处理规则挖掘清单(五类规则) + To-be 流程/CKD/Agentic 工作流 | L5 任务、决策因子、阈值、优先级、硬/软约束 | 故事线 mock、功能上游来源、规则门禁、HITL 触发器 |
| 梳理本体 | Agent 本体设计（对象关系/行动边界/状态迁移） | 实体、关系、动作、HITL 边界、状态机 | 形态架构接触面、Agent 能/不能、HITL 拦截 |

## 二、核心设计引擎（本 Skill 的价值主张）

这是把它做成 Skill（而非模板）的关键——一组「规则 → 产品设计」的自动翻译规则，逐段驱动生成：

1. **决策因子 → 故事线 mock + HITL**：从决策模型类规则提取「因子 / 阈值 / 优先级」，注入**每个画像场景**的演示剧本（用户→思考→调工具→输出）与 HITL 拦截条件。
2. **硬/软约束 → HITL 触发器**：硬约束（不可突破，如可发量）→「写入前必停 + 撤销窗口」；软约束（可仲裁，如成本优先）→「拦截提示 + 出处引用」。自动归类，不事无巨细拦截。
3. **五类规则 → 门禁承接表**：自动生成「规则类型 ×是否识别 × 产品方案承接点 × 承接业务内容 × 备注」；操作流程类由 L5 深度任务回填（不重复）。
4. **必备交互 10 项 → 故事线/功能分配**：把 #1 流式 / #2 工具调用 / #3 思考折叠 / #4 内联组件 / #5 HITL / #6 撤销 / #7 出处引用 / #8 状态徽章 / #9 错误态 / #10 空态 分发到各故事线与功能。
5. **本体对象/动作 → 形态架构接触面**：实体、关系、动作映射为相邻产品的「读/写」接触面与主交互区编排（入口/主交互/周边支撑三区）。
6. **场景画布痛点 → 定位一句话 + 价值高光**：从 `businessGains`（收益字段；“MoS”＝Measure of Success／成功度量，为课程用语，指向同一字段）提炼「四件套·定位一句话」与**每个画像场景故事线**的「业务价值高光」。
7. **画像场景 → 故事线划分**：以《用户画像与典型旅程》的「**画像 × 场景**」为单位划分故事线——每个场景 = 一条**端到端**故事线（从用户目标起点到完成终点），覆盖**主用户全部一期场景 + 1–2 条次要用户场景**；**禁止**按流程阶段（L3/L5）切片，否则原型会被切碎、用户看不到完整旅程。

## 三、输出架构（7 段式）

对齐范例，产出文档含 **meta 头部 + 7 个主体段**（**不含「总览 / 摘要 / 导读」类段落**）。每段字段、数据来源、生成规则如下（字段规范见 `references/schema.yaml`）：

| 段 | 内容 | 数据来源与生成规则 |
|---|---|---|
| meta | 版本 / 更新日期 / 对应业务阶段 / 方法论依据 / 输入依据 | 由执行上下文与输入清单填充 |
| 1 产品定位 | 迭代范围 / 产品形态(B2B自用型) / **四件套**（定位一句话、非目标、主要使用者、Agent 人格） | 定位源自场景画布 `businessGains`（MoS＝Measure of Success／成功度量，课程用语）；非目标=场景边界反向排除相邻系统/相邻画布；Agent 人格=身份+语气+能力边界（来自本体行动边界） |
| 2 产品形态架构图 | mermaid 三大区（入口/主交互/周边支撑）+ 相邻产品接触面 | 引擎⑤：本体实体/关系/动作 → 接触面读/写；相邻产品只画接触面不画协议字段 |
| 3 用户场景演示故事线 | 每条 = 用户画像 / 场景 / 用户目标(Job Story) / 起点→终点 / 演示剧本 / UI组件+必备交互 / 业务内容来源 | 引擎⑦①④：以《用户画像与典型旅程》的**画像 × 场景**为单位；每条**端到端**（起点→终点）；mock 数据取决策因子/阈值（脱敏）；交互标注 #1~#10 |
| 4 业务功能与 UI 组件清单 | 大表（功能名/一句话价值/绑定角色/渲染层/触发方式/UI组件+内容/用户操作/关联故事线/上游来源）+ 必备交互 10 项承诺 | 引擎④：把 10 项交互分发到功能与故事线；上游来源填具体 L5 任务/规则/术语条目 |
| 5 Agent 行为设计 | 5.1 是谁（开场/语气/能力边界） 5.2 让用户看到什么 5.3 何时停下等用户 5.4 怎么撤销与兜底 | 引擎②⑤：硬约束→必停+撤销；软约束→提示+出处；本体行动边界→能力承诺；10 项交互→「看到什么」 |
| 6 五类规则消费门禁 | 表（规则类型 /是否识别 / 产品方案承接点 / 承接业务内容 / 备注） | 引擎③：决策/模板/术语/关键信息提取/关联关系五类各承接；操作流程类由 L5 回填不重复 |
| 7 待确认问题清单 | 表（# / 待确认问题 / 用途与影响） | 自动归纳「阈值口径 / 边界 / 视觉基底 / 相邻系统边界」等悬空决策点 |

## 四、工作流 SOP

1. **确认输入**：读取上游产物清单（理需求 / 场景定义 / 挖知识 / 本体 / **用户画像与典型旅程**）；缺失项向用户确认或标注降级（写明代理）。
2. **抽取知识底座**：从挖知识/本体中提取「规则、决策因子、阈值、硬软约束、实体、关系、动作、状态机」，作为翻译引擎的动力源；从《用户画像与典型旅程》提取「画像 × 场景 × 旅程」，作为第 3 段的骨架。
3. **逐段汇编**：按「输出架构」表，以「核心设计引擎」①→⑦ 逐段生成（先 1 产品定位 → 2 形态架构 → 3 用户场景演示故事线 → 4 功能清单 → 5 Agent 行为 → 6 门禁 → 7 待确认）。**第 3 段必须以《用户画像与典型旅程》的画像 × 场景为单位，不得改回按流程阶段切片。****不生成「总览 / 摘要 / 导读」类段落。**
4. **生成 Markdown**：按 `templates/proposal_template.md` 骨架装配，充实各段内容与 mermaid/表格。
5. **校验**：按「质量校验 Checklist」自查（可用 `scripts/build_proposal.py` 校验结构与列/要素齐全性），不通过则修。
6. **交付落位**：写入 `<公司/业务名>/<场景名>/<公司名>-<场景名>-产品方案.md`，向主 Agent 返回产物清单与「待 FDE 确认」问题。
7. **（可选）生成预览 HTML**：如产物需进统一报告仪表盘或浏览器审阅，运行 `python3 scripts/build_proposal_preview.py "<公司/业务名>/<场景名>/<公司名>-<场景名>-产品方案.md" "<公司/业务名>/<场景名>/<公司名>-<场景名>-产品方案.html"`，生成单文件预览（同目录存放，供 iframe 引用）。此步不影响第 6 步 Markdown 交付。

## 五、质量校验 Checklist（每条须满足）

- [ ] **meta**：版本 / 更新日期 / 方法论依据 / 输入依据齐全。
- [ ] **不含「总览 / 摘要 / 导读」类段落**（文档直接从「1 产品定位」开始）。
- [ ] **第 1 段四件套**：定位一句话、非目标、主要使用者、Agent 人格(身份/语气/能/不能)。
- [ ] **第 2 段**：mermaid 含「入口区 / 主交互区 / 周边支撑区」三区；相邻产品只标读/写接触面。
- [ ] **第 3 段**：以《用户画像与典型旅程》的「画像 × 场景」为单位；覆盖**主用户全部一期场景 + ≥1 条次要用户场景**；每条含「用户画像 / 场景 / 用户目标 / 起点→终点 / 演示剧本 / UI组件+必备交互 / 业务内容来源」；每条**端到端**（起点→终点），**不得**按流程阶段切片；剧本写清 用户→思考→调工具→输出→(HITL/错误/撤销)。
- [ ] **第 4 段**：功能表 9 列齐全；必备交互 10 项(#1~#10)每项至少分配到一处。
- [ ] **第 5 段**：5.1 能力边界与本体行动边界一致；5.3 HITL 与挖知识「硬约束」一一对应（硬→必停，软→提示）；4 个触发类别齐全。
- [ ] **第 6 段**：五类规则(决策/模板/术语/关键信息提取/关联关系)齐全；操作流程类由 L5 回填不重复；每类注明「必须承接 / 必须强化承接」。
- [ ] **第 7 段**：待确认问题 ≥2，含用途与影响。
- [ ] **命名/落位**：`<公司>-<场景名>-产品方案.md` 置于 `<公司/业务名>/<场景名>/`，不落公司根目录。

## 输出呈现铁律（通用 · 强制）

> 产出是给**客户 / 业务方**看的最终报告，不是过程记录。以下五条**违反即返工**。

1. **语言**：一律用**严谨、克制的中文业务咨询语言**——有一说一；**有观点必给依据**（数据 / 规则 / 来源 / 口径）。禁止 AI 味大词与空话堆砌（「赋能、闭环、抓手、深度融合、全方位、数智化」等无实指表述）。
2. **禁止多余英文备注**：中文标题 / 小节后**不得**追加英文装饰（如「业务模式全景 BUSINESS MODEL LANDSCAPE」）。系统名 / 字段名 / 标准缩写（SAP、IF005、DOS、SKU、SLA）可保留；不造装饰性英文。
3. **只输出结论与依据**：**禁止**把过程讨论写进正文——与用户的对话 / 反馈、修订说明、`【不依据原始 idea】` 这类过程标注、跨行业类比的过程推理（如「与快消品的渠道逻辑不同」）、「待确认 / 此处待补 / 讨论点」等制作层信息，一律不进正文。
4. **口径与边界**：不确定的推断标 `[推断]` 并给依据；不臆造数据；假设与阈值标注「领域专家假设值 · 待访谈回填」。
5. **交付前自检**：逐段问「读者能否据此做决策 / 这是否属于我们内部讨论」——不能决策或属内部讨论的内容，删除或移出正文。
