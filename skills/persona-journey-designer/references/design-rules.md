# 生成规则：用户画像与典型旅程

> 本文件规定「画像怎么提取、旅程怎么划分、怎么画」，以及必须避免的错误。
> 核心一句话：**按「工作情境（端末 + 端到端目标）」划分旅程，画像作为旅程的参与者；每条旅程从目标起点走到目标完成终点。**

---

## 一、画像提取（personas）

### 1.1 从哪里来

| 来源 | 提取什么 |
|---|---|
| `opportunity-definition` ② 业务角色及场景 | 目标角色（谁受益）、典型触发场景 |
| `agentic-product-concept-designer` 阶段分工的「人承担」 | 实际动手的角色（判断 / 采集 / 执行） |
| `ai-canvas-generator` userRoles | 补充角色清单 |
| `to-be-process-designer` | 校验是否漏角色 |

### 1.2 分层

- **主用户**：直接使用产品「做事」的人（如一线销售、客服、运营）。
- **次要用户**：管理者 / 协作方 / 后台支撑角色（看结果、审批、维护）。

### 1.3 铁律：角色全覆盖，尤其一线执行角色

- 每类核心角色都要成为**独立画像**，不能合并成「用户」。
- **必须检查一线执行角色**（负责采集 / 录入 / 现场动作的人）是否单独成画像。
  > 典型漏项：主流程在讲「系统怎么跑」，把「一线销售现场做情报采集」这条旅程吞掉了。
- 画像数量通常 2–5 类；少于 2 类说明没拆开，多于 5 类说明没收敛。

## 二、JTBD 方法（场景与 Job）

每个画像先写清它要**完成的事（Job）**，分三类：

| 类型 | 含义 | 提问 |
|---|---|---|
| **功能性 Job** | 要完成的任务 | 「你要完成哪些任务？」 |
| **社会性 Job** | 想被如何看待 | 「你希望被谁、如何看待？」 |
| **情感性 Job** | 想获得 / 避免的情绪 | 「解决它你会是什么感受？」 |

**场景用 Job Story 表述**：`当 [情境] ，我想要 [动机] ，以便 [预期结果]`。

**质量检查**：
- **动词驱动**：Job 是动作（采集 / 判断 / 上报），不是「要有 AI」这类方案。
- **与方案解耦**：说「把现场信息采回来」，不说「用某工具拍照」。
- **够具体**：「提升效率」不算 Job；「一次拜访 5 分钟内把信息采完并结构化」才算。
- **三类都要**：只写功能性 Job 会漏掉社会性 / 情感性动机。

**关键概念（JTBD）**：
- **雇佣 / 解雇**：用户在什么情境下「雇佣」产品、什么情况下会「解雇」它（换成别的方式）。
- **情境（situation）**：Job 由情境触发，不是由用户属性触发——写清「当……的时候」。
- **进步（progress）**：旅程写的是用户「把这件事往前推进」的过程，不是系统功能的执行顺序。

> 方法出处：Clayton Christensen《Competing Against Luck》(2016)；Tony Ulwick, *Outcome-Driven Innovation* (2016)；Alexander Osterwalder, *Value Proposition Canvas* (2014)。

## 三、旅程规则（核心）

### 3.0 旅程划分：按「工作情境（端末 + 端到端目标）」，**不是**按「画像 × 场景」

**一条旅程 = 一个工作情境下的端到端工作过程**。判定顺序：

1. **端末 / 情境优先（硬性）**：**案头（PC）** 与 **现场（移动）** 必须拆成不同旅程——交互形态不同、原型不同，混在一起原型一定做不对。
2. **同一情境 + 同一端到端目标**的连续步骤**合并**为一条旅程。
   > 例：「确认重点对象 → 梳理情报任务并下发」是一条**案头旅程**，不是两条。
3. **一条旅程可跨角色**：写清「**主责角色 + 参与 / 知会角色**」；**不要**把旅程绑死到单一画像。
   > 例：「综合情报分析 → 看机会清单 → 确认并分享」由**区域经理与一线销售共同参与**，是一条旅程。
4. **标注衔接点**：旅程之间说明产出流向。
   > 例：「现场采集」承接「任务下发」、产出流向「综合分析与机会决策」。

> **反例（本 Skill 早期版本的真实错误）**：把「区域经理确认重点对象」与「梳理任务下发」拆成两条旅程、又把「查看综合情报分析 / 看机会清单 / 确认分享」拆成三条——结果是**同一案头情境被切碎、且与移动端采集混在一起**。
> **正确做法**：合并为 3 条——① 案头 · 复盘与任务下发；② 移动 · 现场采集；③ 案头 · 综合分析与机会决策。

### 3.1 起点与终点（硬性）

- **起点 = 目标触发**：什么情境下用户开始「雇佣」产品做事（job arises）。
- **终点 = 目标完成**：用户认为「这件事办完了」的状态（job done）。
- 旅程**必须**从起点走到终点——不是从系统的第一个功能走到最后一个功能。

> 反例：旅程从「打开系统」开始、到「关闭系统」结束 → 这是系统操作，不是用户目标旅程。
> 正例：从「下个周期要定策略但缺现场信息」开始，到「信息齐全、机会清单可判断」结束。

### 3.2 粒度：简要（硬性）

- 每条旅程 **5–7 步**；一行一步 = `阶段 → 角色 → 用户动作 → 触点 → 期望结果`。
- **只写到**「谁（哪个角色）在什么阶段做什么、期望什么」。
- **不写**：UI 组件 / 字段 / 按钮 / AI 交互细节 / 上传文件 / 可见数据（这些属 `ai-product-journey-generator`）。

### 3.3 写法

```
| # | 阶段 | 角色 | 用户动作 | 触点 | 期望结果 |
|---|------|------|----------|------|----------|
| 1 | 触发 | 区域经理 | 周期复盘、要定重点对象 | PC · 复盘看板 | 明确「先锁定重点对象」 |
| 2 | 梳理 | 区域经理 | 把重点对象拆成情报收集任务并下发 | PC · 任务下发 | 一线收到本期采集任务 |
...

**产品介入点**：每条旅程表下补一句，标明产品在旅程的哪几步帮忙——
例如「第 2 步由 Agent 生成任务草稿；第 3 步系统给出结构化结果」。
作用：把「用户旅程」与「原型要做什么」挂上，避免旅程只是用户流程、看不出产品价值。
```

## 四、角色覆盖校验（画像 ↔ 旅程 ↔ To-be 流程）

- 逐条列出：每类画像 **参与了哪几条旅程**、每条旅程对应 To-be 流程的哪些阶段。
- 标注「在主流程中是否显性」：
  - **显性** = 主流程有该角色专门的阶段 / 泳道；
  - **易忽略** = 角色存在但在主流程里没有独立体现（如一线采集角色的现场动作被并入后台处理）。
- **易忽略角色必须补出独立旅程**——这正是本 Skill 相对 `ai-product-journey-generator` 的核心价值。
- 同时校验**端末覆盖**：PC 案头与移动现场是否各有独立旅程，没有混在一条里。

## 五、与 `ai-product-journey-generator` 的分工（不要重复）

| 维度 | 本 Skill | `ai-product-journey-generator` |
|---|---|---|
| 组织 | 按**工作情境（端末）**分旅程，画像作参与者 | 按业务流程主线（跨角色混合） |
| 粒度 | 简要（阶段 / 动作 / 触点 / 期望） | 详细（AI 交互 / 上传 / 可见数据 / 设计意图） |
| 覆盖 | 每类核心角色各一条旅程 | 主流程（易漏角色） |
| 用途 | 原型的场景 / 旅程输入 | 原型的交互细节输入 |

> 本 Skill 里**不要**重复 To-be 旅程的详细交互；发现需要展开细节时，注明「细节见 To-be 旅程」。

## 六、反例（禁止）

- ❌ 只写一类「用户」，不拆画像。
- ❌ 漏掉一线执行角色（采集 / 录入 / 现场）。
- ❌ **按「画像 × 场景」机械拆分旅程**：把同一工作情境的连续步骤切碎，或把 PC 案头与移动现场混在一条旅程里。
- ❌ 把旅程绑死到单一画像（一条旅程可以跨角色，需写清主责与参与角色）。
- ❌ 场景写成功能（「使用 XX 功能」），而不是用户要完成的事。
- ❌ 旅程从「打开系统」到「关闭系统」，而非从目标起点到目标完成终点。
- ❌ 旅程展开 UI / 字段 / AI 交互细节（越界到 To-be 旅程）。
- ❌ 没有「画像 × 旅程」矩阵 / 角色与端末覆盖校验。
