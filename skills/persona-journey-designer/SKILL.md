# Persona Journey Designer (用户画像与典型旅程设计)

在**产品概念设计之后**，以产品经理视角把系统拆成**核心用户画像**，
并为每类画像梳理**典型使用场景**与**简要使用旅程**——回答「谁在用、拿它完成什么、
从什么目标起点走到什么目标完成终点」。

> **性质**：本 Skill 产出的是**按用户画像分视角的场景与旅程清单**，是**原型设计的输入**。
> 它**不展开** UI / 字段 / AI 交互细节（那是 `ai-product-journey-generator` 的活），
> 目的是先确保**每类核心角色都被覆盖**，再让原型按画像逐条落地。

> **与相邻 Skill 的边界（关键）**
> - `ai-product-journey-generator`（To-be 旅程）= **按业务流程主线**，把所有角色混在一条泳道里，
>   每步含 AI 交互 / 上传数据 / 可见数据 / 设计意图的**详细**细节——本质是 **To-be 流程的细化**。
> - **本 Skill** = **按用户画像分视角**，每类画像各自有场景与**简要**旅程，
>   从**用户目标起点**到**目标完成终点**；**强制每类核心角色都有旅程**（含一线执行角色）。
> - `journey-map-generator`（体验旅程图）= **单角色 As-Is 体验分析**（含情感波动 / 触点 / 痛点评分）；
>   本 Skill 是**多角色 To-be 场景与简要旅程**，为原型提供输入。
> - 三者**互补**：本 Skill 保证「角色覆盖 + 用户视角」，`ai-product-journey-generator` 保证「流程细节」，
>   `journey-map-generator` 保证「体验分析」；本 Skill 是原型设计的场景 / 旅程输入。

> [!IMPORTANT] 全局规范（输出形态 / 输出路径 / 铁律）
> **① 输出形态（显式例外）**：本 Skill 输出 **Markdown 主稿 + HTML 预览**（不出 YAML）。
> 原因是产物为叙事型设计稿、而非结构化数据；按 `skill-creator` 规范，属需显式声明的输出例外。
> HTML 由 `scripts/build_persona_journey_preview.py` 从 Markdown 渲染（单文件、可 iframe 内嵌）。
>
> **② 输出路径与命名**：
> - 目录：属具体 AI 场景 → 放入 `<公司/业务名>/<场景名>/`。
> - 文件名：`[公司]-[场景]-用户画像与旅程.md` / `.html`。
> - **禁止**把真实产物写进本 Skill 的 `examples/`（examples/ 仅放脱敏演示样例）。
>
> **③ 铁律（违反即返工）**：画像覆盖所有核心角色；每条旅程**从用户目标起点到目标完成终点**；
> 旅程**简要**（不展开 UI / 字段 / AI 交互）；见 `references/design-rules.md`。

## 三、JTBD 旅程方法（核心）

每条旅程必须**从用户目标的起点到用户目标的完成终点**（不是从系统流程的第一步到最后一步）：

- **Job（要完成的事）** 分三类：**功能性**（要完成的任务）· **社会性**（想被如何看待）· **情感性**（想获得/避免的情绪）。
- **场景用 Job Story 表述**：`当 [情境] ，我想要 [动机] ，以便 [预期结果]`。
- **起点 = 目标触发**：什么情境下用户「雇佣」这个产品开始干活（job arises）。
- **终点 = 目标完成**：用户认为「这件事办完了」的状态（job done）。
- **旅程 = 从起点到终点的推进过程**，每场景 **5–7 步**，一行一步 = `阶段 → 用户动作 → 触点 → 期望结果`。
- **产品介入点**：每场景一句话，标明产品在旅程的哪几步帮忙（把用户旅程与原型挂上）。
- **简要**：只写到「谁在什么阶段做什么、期望什么」，**不写** UI 组件 / 字段 / AI 交互细节。

> JTBD 方法参考：Clayton Christensen《Competing Against Luck》、Tony Ulwick 的 Outcome-Driven Innovation、Osterwalder 的 Value Proposition Canvas（客户 job / pains / gains）。
> 方法细则、Job Story 与旅程示例、反例见 `references/design-rules.md`。

## 四、工作流 SOP

### Step 1 · 收齐输入
- 读取机会点定义（角色 + 场景）与产品概念设计（人承担角色、一期范围、愿景）；
- 可选读取 To-be 流程（用于覆盖校验）。

### Step 2 · 提取核心画像
- 按 `references/design-rules.md`：从「使用者角色」中提取主用户与次要用户；
- **强制检查一线执行角色**（负责采集 / 录入 / 现场动作的角色）是否单独成画像。

### Step 3 · 为每类画像梳理场景与旅程
- 每类画像 2–4 个典型场景；每场景写 Job Story + 起点 + 终点 + 5–7 步简要旅程 + 产品介入点。

### Step 4 · 覆盖校验与矩阵
- 生成画像 × 场景矩阵；对照 To-be 流程做角色覆盖校验，标出易忽略角色。

### Step 5 · 输出 Markdown 主稿
- 按 `references/md-structure.md` 装配，保存为
  `<公司/业务名>/<场景名>/<公司名>-<场景名>-用户画像与旅程.md`。

### Step 6 · 编译 HTML 预览
```bash
python3 scripts/build_persona_journey_preview.py \
  "<公司/业务名>/<场景名>/<公司名>-<场景名>-用户画像与旅程.md" \
  "<公司/业务名>/<场景名>/<公司名>-<场景名>-用户画像与旅程.html"
```

### Step 7 · 交付
- 浏览器打开 HTML：画像总览 → 各画像（卡 + 场景 + 旅程）→ 矩阵 → 覆盖校验 → 原型输入要点；
- 汇报「一期需覆盖的场景 / 旅程」与「易忽略角色」。

## 八、输出呈现铁律（通用 · 强制）

> 产出是给**客户 / 业务方**看的最终报告，不是过程记录。以下五条**违反即返工**。

1. **语言**：一律用**严谨、克制的中文业务咨询语言**——有一说一；**有观点必给依据**（数据 / 规则 / 来源 / 口径）。
   禁止 AI 味大词与空话堆砌（「赋能、闭环、抓手、深度融合、全方位、数智化」等无实指表述）。
2. **禁止多余英文备注**：中文标题 / 小节后**不得**追加英文装饰。系统名 / 标准缩写（CRM、BI、KPI、ROI）可保留；不造装饰性英文。
3. **只输出结论与依据**：**禁止**把过程讨论写进正文——与用户的对话 / 反馈、修订说明、跨行业类比的过程推理等一律不进正文。
4. **口径与边界**：不确定的推断标 `[推断]` 并给依据；不臆造数据；假设与阈值标注「待访谈回填」。
5. **交付前自检**：逐段问「读者能否据此设计原型 / 这是否属于我们内部讨论」——不能指导原型或属内部讨论的内容，删除或移出正文。
