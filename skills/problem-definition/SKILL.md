# Problem Definition (业务问题定义 · 8 要素)

此技能用于在完成「现状泳道图 + 痛点挖掘 + 根因分析」之后，把**一个聚焦痛点的根因**
用 **8 个结构化要素**定义成一个“可取证、可量化、可归因”的**业务问题（Problem Statement）**，
作为后续 AI 机会点挖掘与 To-be 设计（`ai-opportunity-map-generator` / `ai-canvas-generator` /
`deep-task-flow-analyzer`）的**问题定义层输入**。

> 定位与上下游：
> - **上游输入**：`business-process-deep-analyzer`（现状泳道图+痛点）、根因分析（5-Why）产出。
> - **本 Skill**：把一个痛点问题按 8 要素结构化定义（一人一句、有证据、有量化）。
> - **下游衔接**：`ai-opportunity-map-generator` / `ai-canvas-generator`（基于该问题挖机会/出画布）、
>   `business-rule-miner` / `deep-task-flow-analyzer`（问题定义 → 规则/任务）。

> [!IMPORTANT] 全局规范（双重输出 / 输出路径 / 视觉设计）
> 当你使用此 Skill 时，必须**同时**输出两个部分：
> 1. **结构化 YAML**：用于下一步的自动化处理和数据存档。
> 2. **交互式 HTML**：用于最终用户的直观审查与演示。HTML 已集成「复制原始 YAML」。
>
> **输出路径与命名规范 (Output Path & Naming Convention)**:
> - **目录**: 输出到 `<公司/业务名>/` 业务级目录；若强耦合某场景，可放 `<公司/业务名>/<场景名>/`。
> - **文件名**: `[公司/业务名]-[价值段/环节]-问题定义.html`；YAML 同理
>   （例如：`X大客户销售-询价报价与成本测算-问题定义.html`）。
> - **禁止**将产物输出到 Skill 的 `examples/` 目录（examples/ 仅存放演示样例）。
>
> **视觉设计规范 (Visual Design Standard)**:
> - 默认按本 skill `references/schema.yaml` + `templates/problem_definition_layout.html` 输出。
> - 浅色底 (Light Mode)；内容区撑满容器；8 个要素以编号卡片纵向排布，逐条可读。
> - 顶部为「标题 + 核心问题一句话 callout + 元信息 chips」；末尾附「痛点→根因→问题」小结区。

## 核心架构

采用 **LLM -> YAML -> Python -> HTML** 的解耦架构：
1. **LLM**: 解析输入（根因分析/痛点详情），按 `references/problem_definition_prompts.md`
   推导出 8 要素 YAML。
2. **Compiler**: `scripts/build_problem_definition.py` 解析 YAML，结合
   `templates/problem_definition_layout.html` 生成问题定义报告；自动缩略、格式化与防呆清洗。

## 8 要素结构（核心）

| # | 要素 | 定义 | 判定口径 |
|---|------|------|---------|
| ① | **一句话问题描述** | 用一句话把问题+核心缺陷+后果说清 | 主谓语明确、含“导致…恶化/根因” |
| ② | **业务角色和场景** | 参与者 + 何时/何地发生 | 角色清单 + 一个典型场景 |
| ③ | **遇到的问题** | 具体现象（可观察） | 每条现象可对应上游泳道卡 |
| ④ | **问题根因** | 为什么发生（承接 5-Why），**按根因类别分组列出** | 每条命中根因分类（见下节），非个人态度 |
| ⑤ | **发生频度** | 多久发生/多大批量 | **必须量化**：频次 × 基数 × 年化量级（见下节） |
| ⑥ | **影响范围** | 覆盖哪些角色/渠道/系统 | 角色链路 + 渠道 + 系统边界 |
| ⑦ | **每次发生对业务的影响** | 单次代价 | **必须量化**：有单位（时长/成本/概率）+ 估算口径 |
| ⑧ | **累计对业务影响** | N 次叠加后的全局代价 | **必须量化**：年化总量 + 金额区间 + KPI 承压 |

## 根因分类（Root Cause Taxonomy · 强制）

**5 Why 逐层下钻，末层（结构性根因）必须落到下表 5 类之一**；④ 问题根因必须**按类别分组列出**，
不得写成一段笼统描述（如「缺规则结构化 + 数据打通 + 闭环预警的能力」这类不是根因）。

| 代码 | 类别 | 判定特征 | 典型表现 |
|------|------|----------|----------|
| `RC-PROC` | **流程机制缺失** | 缺规范的流程、职责分工、执行频次、上报路径、考核与激励机制 | 谁采 / 采什么 / 多久采 / 上报给谁未定义；采集后无反馈、无激励；过程不考核 |
| `RC-KNOW` | **知识与规则缺失** | 判断依据、分类分级标准、规则、阈值、口径未定义或未沉淀 | 风险/问题分类分级标准缺失；判断与预警规则未定义；信息清单与口径不清 |
| `RC-DATA` | **数据分散 / 口径不一** | 数据分散在多系统、多来源，口径不一，未统一汇聚 | 同一指标多个来源；跨系统手工核对；口径各说各话 |
| `RC-MANUAL` | **纯人工、高耗时** | 无工具 / 自动化支撑，靠人工重复操作 | 逐户人工提炼、逐份手工汇总、逐条人工比对 |
| `RC-EXPERT` | **高度依赖专家经验** | 判断 / 决策依赖个人经验，不可复制、不可传承 | 靠资深员工经验拍板；新人上手慢；产出质量随人而异 |

**铁律**：

- 每个根因簇标注**一个主类别**（`category` 用上表代码），必要时可补 `categoryNote` 说明副类别。
- 5 Why 的末层（`root: true`）必须命中上表某一类；命中不了说明还没挖到底。
- **禁止**把「系统集成 / 数据打通」直接当根因——若集成已在推进，应归入 `RC-KNOW` 或 `RC-PROC`，并具化到「缺哪条规则、缺哪份清单、缺哪项机制」。
- 根因写到**可执行粒度**：缺什么、谁缺、缺到什么程度。

## 量化估算规范（E5 / E7 / E8 · 强制）

**⑤⑦⑧ 三个要素必须给出量化预估**，禁止只写「很慢 / 很多 / 经常 / 影响大」这类形容词。
拿不到实测值时，给**估算口径 + 假设值 + 区间**，并标注 `[推断]` 或「领域专家假设值 · 待访谈回填」。

| 要素 | 必须给出 | 估算公式 | 标注要求 |
|------|----------|----------|----------|
| ⑤ 发生频度 | 频次 × 基数 × **年化量级** | 客户数（基数）× 指标数 × 跟进频次 → **户次/年**、**判断点/年** | 访谈值与假设值分开标注 |
| ⑦ 单次影响 | 单次**工时 / 成本 / 损失**（带单位） | 单户人工工时；单户年额 × 漏判/延误比例 | 比例类标「领域专家假设值 · 待访谈回填」 |
| ⑧ 累计影响 | **年化总量 + 金额区间 + KPI 承压** | 户次/年 × 单次工时 → 人时/年 → 人年；年额 × 比例 → 金额区间 | 全部标 `[推断]` + 写明估算口径 |

**铁律**：

1. **必须写估算口径**：基数、单价、比例、折算系数各自来自哪里（访谈值 / 公开数据 / 假设值）。
2. **区间优于点值**：给上下限（如「约 530–1,050 万元/年」），不给虚假的精确点值。
3. **折算要有系数**：人时→人年按 `1,760 人时/人年`；工时/金额按客户数、订单量等基数折算。
4. **⑧ 必须落到 KPI**：年化代价要能对上该环节的关键指标承压，并说明战略后果。
5. **不臆造数据**：无依据的数字一律标假设值，并注明「待访谈回填」。

**写法模板**：

```
⑤ 发生频度：<基数> × <频次> → 约 <N> 户次/年；<N> × <指标数> → 约 <M> 判断点/年。
   [估算口径：基数与指标数为访谈值；频次为领域专家假设值 · 待访谈回填]
⑦ 单次影响：单次约 <a–b> 小时/户次 [推断]；单次损失约 <x–y> 万元（<基数> × <比例>）[推断]。
⑧ 累计影响：<N> 户次/年 × <a–b> 小时 ≈ <X–Y> 人时/年（约 <p–q> 人年）[推断]；
   金额约 <M1–M2> 万元/年（<口径>）[推断]；导致 <KPI 清单> 承压。
```

## 工作流 SOP

### Step 1 · 解析输入（痛点 / 根因 / 现状泳道）
- **优先**：读取上游 `business-process-deep-analyzer` 现状泳道图 YAML、痛点明细表与 5-Why 根因分析。
- **兜底**：用户以自然语言描述“哪个环节 + 痛点 + 根因”时，自行拆为 8 要素。

### Step 2 · 推导问题定义 YAML（LLM 产物）
- 严格遵循 `references/problem_definition_prompts.md` 的 8 要素铁律与字段约束。
- **产物保存到 `<公司/业务名>/` 目录**，命名 `[公司/业务名]-[价值段/环节]-问题定义.yaml`。

### Step 3 · 编译输出 HTML
```bash
python3 scripts/build_problem_definition.py examples/<标识>.yaml examples/<标识>.html
```

### Step 4 · 最终交付
告知用户浏览器直接打开该 HTML 即可查阅：标题 → 一句话问题 callout → 元信息 chips →
①~⑧ 各要素卡 → 「痛点→根因→问题」小结区。顶部可「📋 复制 YAML」。

## 输出呈现铁律（通用 · 强制）

> 产出是给**客户 / 业务方**看的最终报告，不是过程记录。以下五条**违反即返工**。

1. **语言**：一律用**严谨、克制的中文业务咨询语言**——有一说一；**有观点必给依据**（数据 / 规则 / 来源 / 口径）。禁止 AI 味大词与空话堆砌（「赋能、闭环、抓手、深度融合、全方位、数智化」等无实指表述）。
2. **禁止多余英文备注**：中文标题 / 小节后**不得**追加英文装饰（如「业务模式全景 BUSINESS MODEL LANDSCAPE」）。系统名 / 字段名 / 标准缩写（SAP、IF005、DOS、SKU、SLA）可保留；不造装饰性英文。
3. **只输出结论与依据**：**禁止**把过程讨论写进正文——与用户的对话 / 反馈、修订说明、`【不依据原始 idea】` 这类过程标注、跨行业类比的过程推理（如「与快消品的渠道逻辑不同」）、「待确认 / 此处待补 / 讨论点」等制作层信息，一律不进正文。
4. **口径与边界**：不确定的推断标 `[推断]` 并给依据；不臆造数据；假设与阈值标注「领域专家假设值 · 待访谈回填」。
5. **交付前自检**：逐段问「读者能否据此做决策 / 这是否属于我们内部讨论」——不能决策或属内部讨论的内容，删除或移出正文。
