# 输出骨架：待确认稿的结构与写法

> 本文件规定《访谈信息整理（待确认稿）》的**统一结构、归位口径与文末清单模板**。
> 目标是让每一份稿子都「同一套骨架、同一个口径、可直接核对」。

---

## 一、整体结构

```
① 文首元信息块（blockquote + 四要素）
② 正文（提纲归位 或 链路归位）
③ 文末清单（待确认与本次未涉及 / 待澄清 / 已纠正项）
```

---

## 二、文首元信息块（固定）

```markdown
# <客户> · <场次>访谈信息整理

> 以下依据 <日期> <场次>访谈整理，按 <提纲结构 / 业务链路> 归位，仅记录访谈中提到的实际情况。
> 请核对是否与真实情况一致；如有出入、遗漏或需要补充的地方，可直接在对应位置标注。

**受访人**：<姓名（角色）；未具名写「姓名待确认」>
**访谈时间**：<日期>（约 <时长>）
**记录来源**：<录音文件名>（<日期> <时段>，<时长>）+ <人工记录文件名>
**整理口径**：仅将受访者所述 facts 按 <结构> 归位，不做提炼、推断或评价；未答 / 未问到的题项标注为「未提及」。
```

> **铁律**：文首必须出现「仅记录实际情况 / 不做提炼、推断或评价」的口径声明——
> 这是「待确认稿」区别于分析报告的根本标志。

---

## 三、正文的两种归位口径

### 口径 1 · 提纲归位（有提纲时，默认）

- 一级标题 = 提纲章节（如「一、角色与背景」「二、核心业务全周期」…）。
- 二级标题 = 提纲小节（如「1.1 职责与团队」），内容**按题号顺序**归位。
- 每题写法：先给事实，再补量化；未提及项紧随其后标注。
- 如提纲带价值流分段对照，文末可附「提问与分段归位表」（已获得事实 + 缺口），便于下游对齐。

### 口径 2 · 链路归位（无提纲 / 提纲不适用时）

按该场次的**业务链路**设一级标题。链路**随场景而定**，不写死；常用形态：

```
一、受访人与业务概况
二、现状数据 / 信息现状
三、信息收集
四、分析与判断
五、机会识别与行动制定
六、执行、记录与反馈
七、对未来的期待
```

> 采用链路归位时，**必须在文首说明**所用的链路（如「按『现状数据 → 信息收集 → 分析判断 →
> 机会识别 → 行动制定 → 执行反馈』链路归位」）；链路应与该业务的实际环节一致，不套用无关模板。

---

## 四、正文写法规范

- **加粗关键事实与数字**：`**N 家 <对象>**`、`**X 万元**`。
- **保留受访人原话**：用引号照抄，如「我自己都拿不到，凭什么质问他」。
- **量化如实**：数字带单位；模糊度保留（「七八千」不写成 7500）。
- **未提及**：句末紧跟「：**未提及**」或「**本次访谈未涉及**」。
- **存疑专有名词**：写「转写原文（待澄清）」或「<最可能写法>（待确认）」。
- **他人补充**：标注来源，如「（在场同事补充）」。
- **设想 / 期望**：标注「（属受访人设想，尚未落地）」。

---

## 五、文末清单（三块，交付物的核心）

### 5.1 「待确认与本次未涉及」（必须）

集中列出本场次所有**需要业务方回填 / 确认**的项：

```markdown
## 待确认与本次未涉及

- **受访人身份**：<未具名 / 称呼冲突 → 待确认说明>
- **未问到的题项**：<提纲中问了但访谈未涉及的题，逐条列>
- **尚未落地的设想**：<受访人提到但未落地的机制 / 工具>
- **数字 / 口径待确认**：<单位不明或口述有出入的项>
```

### 5.2 「待澄清（录音转写存疑）」（必须）

集中列出**转写存疑的专有名词**，供业务方澄清：

```markdown
## 待澄清（录音转写存疑）

| 位置 | 转写原文 | 疑似正确 | 需澄清 |
|---|---|---|---|
| 三、信息捕捉 | 网放新 / 网放心 | 网放鑫 | 平台正式名称 |
| 五、分析与判断 | 华东云宏 / 云红 | 同一家？ | 是否同一客户 |
| 全文 | 某产品名（转写） | ？ | 是否确有此产品（未见于产品知识库，标 [待核实]） |
```

> 人名、产品名、机构名、平台名、系统名、关键业务术语，凡无法 100% 确定的，一律进本表。

### 5.3 「已纠正项（录音转写明显错字）」（有则列，无则删）

```markdown
## 已纠正项（录音转写明显错字）

- 「环东」→「环通」（公司系统名）
- 「纯消」→「纯销」（业务术语）
```

---

## 六、交付形态

- **默认只输出 Markdown**（本 Skill 的显式输出例外）。
- 如业务方需要更易读的版本，可在 Markdown 基础上另行转换（HTML / PDF 等），
  但**不在本技能范围内**，由用户另行指定。

---

## 七、常见错误（禁止）

- ❌ 文首缺口径声明，读起来像分析报告。
- ❌ 用「大概 / 推测」的推断替代「未提及」标注。
- ❌ 把提纲的提示词 / 话术当成受访人所述事实。
- ❌ 把录音里的错名字直接写进正文结论（应进「待澄清」）。
- ❌ 文末没有「待澄清」清单——这是本稿最常被业务方使用的部分。
